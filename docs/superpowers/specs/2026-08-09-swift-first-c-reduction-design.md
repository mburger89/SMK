# Swift-First C Reduction — Design Spec

## Goal

Reduce the amount of hand-written project C code in SMK by applying this project's already-established Swift/C split pattern (`@_extern(c, "fn")` / `@_cdecl("fn")` for scalar-parameter C calls, hand-rolled Swift structs for simple config structs, C retained only where genuinely required) to files that predate that pattern or were never revisited after it was adopted.

## Background

SMK's language mix is currently skewed toward C (roughly 9,800 C/H lines vs. 2,530 Swift lines, in-repo, git-tracked). A line-by-line survey (not just GitHub's byte-based language stats, which also count Markdown/CMake/Kconfig) shows that **~67% of all C (≈6,570 lines) is not really "our" code**:

- `Sources/CJSON/cJSON.c` + header (3,534 lines) — vendored JSON parser
- `ports/nrf52840/platform/sdc_hci_dispatch.c`/`.h`/`_wrappers.h` (2,211 lines) — vendored/adapted from Nordic's `nrfconnect/sdk-nrf`, deliberately kept byte-identical to a pinned upstream commit for correctness (see `docs/superpowers/plans/2026-08-09-nrf52840-support.md`, Task 6)
- `ports/rp2040/platform/cyw43439_patchram.c`+`.h` (648 lines) — a firmware binary blob as a C array, sourced from Murata's public `cyw-bt-patch` repo — no logic to port

Of the remaining ~3,200 lines that are genuinely project-authored, some were already ported to Swift this session (`GPIOInit.swift`, `SmkConfig.swift` on ESP32-C6; `GPIOInit.swift`, `UsbHid.swift`, `MpslGlue.swift` on nRF52840; `BatteryMonitor.swift`'s ADC math on ESP32-C6), but several files — mostly on RP2040, plus a few cross-platform ones — predate the Swift-first preference (adopted mid-way through the nRF52840 port, see `feedback_prefer_swift_over_c` memory) and were never revisited.

This is a mechanical/incremental effort applying an already-proven pattern, not new architecture. The interesting judgment calls are per-file: does this specific C API's signature shape allow a clean scalar-only or simple-struct Swift port, or does it need a struct-of-function-pointers "vtable" that has to stay C (the established `hci_transport_t` exception)?

## Scope

**In scope**: every git-tracked `.c`/`.h` file under `Sources/` and `ports/*/platform/` that is project-authored (not vendored, not a data blob) is evaluated for a Swift port, full or partial.

**Out of scope**: this plan does not restructure the build system (no new build modes, no real Swift module boundaries — every target keeps compiling as one flat `swiftc -wmo` invocation, matching the existing pattern) or touch `Kconfig.projbuild`, though `CMakeLists.txt` source-list edits are expected and necessary wherever a file moves, gets renamed, or changes from a `.c`/`.h` pair to a `.swift` file. This plan does not change any HID report formats, wire protocols, or GATT service definitions (byte-for-byte identical firmware behavior is a hard constraint — this is a language-of-implementation change, not a behavior change), and does not attempt hardware bring-up or fix any of the pre-existing "not yet hardware-verified" gaps on RP2040/nRF52840.

BTstack GATT/HID setup files, same class as `ports/nrf52840/platform/ble_hid_sdc.c` (this session's highest-risk task, which needed a dedicated high-scrutiny review and a 4-Critical-bug fix round).

| File | Lines | Disposition |
|---|---|---|
| `ports/rp2040/platform/ble_hid.c` | 135 | Port non-struct logic (`packet_handler`, `send_pending`, `init_ble_hid`, `send_keyboard_report`) to Swift. **Lower risk than `ble_hid_sdc.c`**: this file has no `hci_transport_t`-style vtable struct at all — `cyw43_arch_init()` owns BTstack's transport setup internally, so there's no struct-of-function-pointers construction anywhere in this file. ### Permanent C Exceptions (not attempted, any tier)

| File(s) | Why |
|---|---|
| `Sources/CJSON/cJSON.c`+`.h` (3,534 lines) | Vendored third-party library. |
| `ports/nrf52840/platform/sdc_hci_dispatch.c`/`.h`/`_wrappers.h` (2,211 lines), `sdc_bt_compat.h` (193 lines) | Vendored/adapted, deliberately byte-identical to a pinned upstream commit — already reviewed and documented this session (Task 6 of the nRF52840 plan). |
| `ports/rp2040/platform/cyw43439_patchram.c`+`.h` (648 lines) | Firmware binary blob as a C array — no logic to port, porting it would just move where the same bytes live. |
| `Sources/components/led_strip_encoder.c`+`.h` (162 lines) | Struct-embedding/vtable C idiom (`__containerof`, `rmt_encoder_t base` field embedding a base-class-style interface) — the same class of thing as `hci_transport_t`, and no safe partial split exists since the whole file *is* the vtable implementation. |
| `Sources/components/kb_main.c`'s Unicode-stdlib stubs + `app_main()`; `ports/rp2040/platform/platform_glue.c`'s same stubs + `main()`; `ports/nrf52840/platform/platform_glue.c`'s `main()` | `main()`/`app_main()` are real C-runtime entry points (established, permanent exception across every target this whole session). The Unicode-stdlib linker stubs (`_swift_stdlib_getNormData` etc.) satisfy references Swift's *own* Embedded runtime makes before/during its own bootstrap — defining these *as* Swift `@_cdecl` functions would introduce a real bootstrapping-order risk (does the Swift runtime's linker resolution of its own stub symbols work correctly if the stub is itself Swift code relying on that same runtime being up?) for zero benefit, since they're already one-line no-op bodies. `posix_memalign` (RP2040 only) is the same category — it's what Swift's own allocator calls to get heap memory in the first place. |
| `ports/*/platform/btstack_config.h`, `ports/*/platform/tusb_config.h`, `ports/nrf52840/platform/nrfx_glue.h` | Pure C-preprocessor feature-flag headers consumed by vendored C source's own `#if`/`#ifdef` checks (BTstack, TinyUSB, nrfx) — there is no meaningful Swift equivalent for a header whose entire content is `#define`s read by someone else's C preprocessor. |
| `ports/nrf52840/platform/ble_hid_sdc.c` | Already has its own documented, reviewed C exception from this session (struct-heavy BTstack API, highest-risk task, no hardware to verify a translation against) — revisiting it is explicitly named as a future follow-up in that file's own header comment once nRF52840 hardware exists, not part of this plan. |

## Testing / Verification Strategy

This plan changes implementation language, not behavior — the bar is **provably identical firmware behavior**, verified the same way every task in the nRF52840 plan was:

1. **Per-task build verification**: every task rebuilds and links every target it could plausibly affect. Tier 1/2 RP2040 changes rebuild `./build_rp2040.sh pico`/`pico_w` (and `pico2`/`pico2_w` if touched); ESP32-C6 changes rebuild via `idf.py build` (real ESP-IDF is installed on this machine at `~/.espressif/v6.0.1/esp-idf` — a prior "known toolchain break" noted in this project's memory did not reproduce when last tried and should be re-checked, not assumed still broken); nRF52840-touching changes (none currently planned, but the shared `smk_keymap_protocol.c`/`smk_keymap_store.c` de-duplication touches all three) rebuild `./build_nrf52840.sh`.
2. **Symbol-level verification**: for each ported function, confirm via `nm`/`objdump` (matching this session's established practice) that the Swift-defined symbol is what's actually linked, not a stale C stub or a silently-unresolved reference — this is how Task 5's missing-ISR-handler bug and Task 8's `USBD_IRQHandler` bug were caught, both invisible to "the build succeeded."
3. **New host tests**: `smk_keymap_protocol.c`'s dispatch logic and the de-duplicated CRC32/frame-parsing logic moving into `Sources/SMKCore/` should get real `Tests/SMKCoreTests/` coverage as part of the task that moves them — malformed packets, truncated frames, CRC mismatches, boundary lengths (matching the existing test suite's style, e.g. `LayerEngineTests`'s invalid-keymap-fallback coverage).
4. **Verify-against-real-source discipline**: every task's implementer verifies the plan's claimed C API signatures against the real installed/vendored headers before writing `@_extern(c, ...)` declarations, rather than trusting this spec's descriptions — this project's established, repeatedly-load-bearing practice this session (caught real bugs in nearly every nRF52840 task).
5. **Review intensity scales with tier**: Tier 1 tasks get a standard task review. Tier 2 tasks get a standard review with explicit attention to struct-layout correctness. Tier 3 tasks (`ble_hid.c`, `ble_hid_kbd_uart.c`) get the same dedicated high-scrutiny review Task 7 of the nRF52840 plan got, and should be planned expecting at least one fix round.
6. **Final whole-branch review**: same as the nRF52840 plan — a dedicated pass after all tasks land, checking cross-task integration (do the now-Swift `smk_keymap_store.c` variants and the now-Swift `smk_keymap_protocol.c` compose correctly across all three ports?) and doc accuracy (`CLAUDE.md`'s per-file tables need updating for every file that changes language or moves to `SMKCore`).

## Non-Goals

- No behavior changes. HID report formats, BLE GATT structure, wire protocols, and hardware timing must be identical before and after.
- No attempt to fix pre-existing "not yet hardware-verified" gaps on RP2040/nRF52840 as a side effect of touching nearby files.
- No new abstractions or generalized "Swift wrapper framework" — each port keeps its own thin `@_extern(c, ...)` bindings, matching the existing flat, no-module-boundary style throughout this codebase (`Package.swift` remains IDE/LSP-only, never the real build).
