# Swift 6.4 Embedded Adoption — Design

Date: 2026-10-09
Status: draft, awaiting review

## Intent

Move every SMK firmware build from Swift 6.3.x to **Swift 6.4.0-RELEASE** and adopt
every Embedded Swift language/library feature that applies to this codebase
("maximal adoption"), while keeping on-device behaviour identical apart from one
explicitly approved change (the 256-position matrix cap, Phase 3).

Execution is phased; each phase is implemented by parallel subagents orchestrated
by a Workflow and must pass the same build/size gate before the next starts.

### What the user decided

- Approach: phased (Phases 0–4), one workflow per phase, gate between phases.
- Volatile MMIO: **swift-mmio** (not the underscored `_Volatile` module, not the C shims).
- Size budget: each target may grow **≤ 2 %** in flash (`.text + .rodata + .data`)
  and static RAM (`.data + .bss`) relative to its **6.4 baseline**.
- Concurrency: spiked before this spec; **out of scope** (see "Concurrency" below).
- Matrix cap of 256 positions: approved.

### Success criteria

1. All 11 builds succeed on 6.4.0-RELEASE from a clean configure:
   esp32c6 (smk_kbd), pico, pico_w, pico2, pico2_w, smk_kbd_rp2040,
   nrf52840dk, feather_nrf52840, samd21, stm32f4, stm32wb.
2. `SMK_HOST_TESTS_ONLY=1 swift test` passes.
3. Every target within the 2 % size budget vs. its 6.4 baseline.
4. No 6.3-only or snapshot-only requirement remains in build files or CLAUDE.md.
5. Hardware smoke test (manual, by the maintainer, after Phase 4): smk_kbd
   (ESP32-C6) boots and pairs over BLE; a Pico and the XIAO RP2350 boot and enumerate
   as "SMK Keyboard". Other ports are build-only today and stay build-only.

## Research summary (what 6.4 actually changes)

Verified by compiling probes against both 6.3.3 and 6.4.0 for riscv32, armv6m,
armv7em and armv8m.main (probe sources in the session scratchpad, not the repo).

| Feature | 6.4 status | Matters here because |
|---|---|---|
| armv8m.main stdlib | **new** — ships in the release toolchain | RP2350 (pico2/pico2_w) no longer needs a dev snapshot |
| `any P` existentials, `Any`, metatypes | **new** (limits: no cast *to* existential, no generic methods on one, no opening) | enables Phase 4 protocol-based transports/stores/LED chains |
| untyped `throws` / `any Error` | **new** | not used — typed throws preferred (no allocation) |
| `@c`, `@section`, `@used` | stable (already in 6.3.3) | replace `@_cdecl`/`@_section`; drop `SymbolLinkageMarkers` |
| `InlineArray`, `Span`/`RawSpan`/`MutableSpan`, `~Copyable` | stable (already in 6.3.3) | Phase 3 / Phase 4 |
| Embedded mode | still experimental flag | keep `-enable-experimental-feature Embedded` |
| `@_extern(c)` | still experimental flag, no stable replacement | keep where no bridging header covers the symbol |
| `.pointee` MMIO polling | unchanged — empty poll loops still deleted | swift-mmio in Phase 2 |
| Unicode `_swift_stdlib_*` stubs, `posix_memalign` | still required | keep `embedded_swift_glue.c` / `kb_main.c` stubs |

## Phase 0 — Toolchain and the validation gate

**Toolchain discovery.** The six CMake toolchain-discovery blocks
(`main/CMakeLists.txt:52-115`, `ports/rp2040/CMakeLists.txt:32-104`,
`ports/{samd21,nrf52840,stm32f4,stm32wb}/CMakeLists.txt`) are near-identical; they
move into one `cmake/FindEmbeddedSwiftc.cmake` included by all six. New behaviour:

- `SWIFTC_PATH` (cache var, then env) still overrides everything.
- Otherwise glob `~/Library/Developer/Toolchains` and `/Library/Developer/Toolchains`,
  **sort by parsed version, newest first**, skip `swift-DEVELOPMENT-SNAPSHOT-*`
  unless `SMK_ALLOW_SNAPSHOT=ON`, skip `swift-latest` (a symlink duplicate).
- Probe = `-print-target-info` **and** a `-typecheck` of a trivial Embedded file for
  the build's triple (ESP32-C6 gains the typecheck probe it currently lacks).
- Require `swiftc --version` ≥ 6.4; fail configure with a message naming the
  minimum and the `SWIFTC_PATH` override otherwise.
- ESP32-C6's `find_program(swiftc)` fallback is removed (it bypasses the version floor).

Existing build dirs have 6.3.1 (or the snapshot, for pico2/pico2_w) cached in
`SWIFTC_PATH`; the gate script always configures fresh, and CLAUDE.md tells
developers to delete their `build*/` dirs once.

Documentation: remove the RP2350 dev-snapshot prerequisite and the 6.3.x comments in
`ports/rp2040/CMakeLists.txt:56-62`, `ports/samd21/CMakeLists.txt:54`, etc.; CLAUDE.md
prerequisites say "Swift 6.4.0-RELEASE or later" for all targets.

**Gate script `tools/build_all.sh`.**

- Clean-configures and builds all 11 targets into `build_gate/<target>/` (never
  touches developers' own `build*/` dirs), then runs `SMK_HOST_TESTS_ONLY=1 swift test`.
- Records `.text/.rodata/.data/.bss` per target via `arm-none-eabi-size -A` /
  `riscv32-esp-elf-size -A` into `docs/superpowers/notes/swift64-sizes.md`
  (a table appended per run, labelled with phase and commit).
- `--baseline` writes the reference row; a normal run compares against it and exits
  non-zero if any target exceeds +2 % flash or static RAM.
- `--check-polls` (Phase 2+) disassembles named poll functions (list in the script)
  and fails if any compiles to a loop-free body.
- Targets whose external SDK isn't installed are reported as SKIPPED, not passed;
  the gate requires all 11 on the maintainer's machine.

Phase 0 produces two baselines: one with 6.3.1 (`SWIFTC_PATH` forced) and one with
6.4.0 and no source changes. The 6.3→6.4 delta is reported but is not gated
(compiler-driven); the 6.4 row becomes the reference for Phases 1–4.

## Phase 1 — Stable attributes

- `@_cdecl("x")` → `@c(x)` (74 sites, 22 files). Where the Swift name equals the C
  name, plain `@c`.
- `@_section(...)` → `@section(...)` (3 sites, `Sources/smk/LedStripDriverRMT.swift`);
  any `@_used` → `@used`; remove `-enable-experimental-feature SymbolLinkageMarkers`
  from `main/CMakeLists.txt`.
- `@_extern(c, ...)` (181 sites) stays. For each, if a bridging header already imports
  the same C declaration, delete the Swift redeclaration instead of keeping both.
- No behaviour change; symbol names must be identical — the gate additionally diffs
  `nm --defined-only` exported C symbols per target before/after.

## Phase 2 — swift-mmio

**Build integration.**

- Vendor swift-mmio as a git submodule at `third_party/swift-mmio`, pinned to a
  release tag that builds with 6.4. `Package.swift` switches from
  `.package(url:..., branch: "main")` to `.package(path: "third_party/swift-mmio")`.
- New `cmake/SwiftMMIO.cmake`, included by all six CMakeLists:
  - Builds the `MMIOMacros` plugin **for the host** once via
    `swift build -c release --product MMIOMacros --package-path third_party/swift-mmio`
    using the same toolchain, output cached under `build_gate/_host/` or the
    build dir; exported as `SMK_MMIO_PLUGIN`.
  - Appends swift-mmio's `MMIO` sources to each target's flat Swift source list and
    its `MMIOVolatile` C header directory to `-Xcc -I`.
  - Adds `-load-plugin-executable ${SMK_MMIO_PLUGIN}#MMIOMacros` to Swift flags.
- `MMIO` compiles flat into each target (no `import MMIO`), same as SMKCore. If its
  sources rely on module-qualified names that break when flattened, fall back to
  compiling `MMIO` as a separate module (`-emit-module`) per target and adding
  `-I` for the module — decided during Phase 2 implementation, recorded in the plan.

**Register conversion.**

- Each port's register-touching files — `GPIORegisters.swift` (all ports),
  `ClockInit.swift` (stm32f4, stm32wb, samd21), `HwIpcc.swift` (stm32wb),
  `UartDebug.swift` (samd21) and any other `.pointee` MMIO site — define
  `@RegisterBlock`/`@Register` structs **by hand**, covering only the registers and
  fields actually used (no SVD generation).
- All `UnsafeMutablePointer<UInt32>(bitPattern:)` MMIO and `.pointee` register
  accesses are replaced. `smk_cpu_nop()` and `smk_mmio_read32()` are deleted; the
  `cortex_m_intrinsics.c` files keep only PRIMASK/SEV/WFE wrappers.
- `.pointee` uses that are not MMIO (C buffers, callback contexts) are untouched.
- CLAUDE.md's "Register-polling loops written in Swift MUST call an opaque C
  function" rule is replaced by "MMIO goes through swift-mmio registers, never
  `.pointee`", keeping the history of why.
- Gate adds `--check-polls` over the ClockInit poll loops on stm32f4/stm32wb/samd21.

## Phase 3 — InlineArray and Span

- `HIDReport.keys: [UInt8]` → `InlineArray<6, UInt8>`; hand-written `Equatable`.
- `DebouncedMatrix`: counters → `InlineArray<256, UInt8>`; stable state and raw scan
  → a 256-bit `KeyBitset` (`InlineArray<8, UInt32>`) in SMKCore. `KeyMatrix` scans
  into a `KeyBitset`; `KeyEventProcessing` consumes bitsets. No per-tick allocation.
- **Approved behaviour change:** `decodeKeymapPayload` rejects
  `rowCount × colCount > 256` with a typed error. Largest current board: 60.
  `Config(payload:)` asserts the same bound.
- Per-report heap buffers (`[UInt8](repeating:)` in `BleHelper.swift`,
  `WiredHidUart.swift`, `ports/samd21/UsbHid.swift`, …) → stack `InlineArray`,
  passed to C via `withUnsafeBufferPointer`/`span`. Long-lived global buffers
  (`LedStripDriverRMT/PIO`, `BleHidGatt`, `BleHidSdc`, `KeymapStoreNVS`) → fixed-size
  `InlineArray` statics sized from existing constants.
- Byte-parsing APIs take `Span<UInt8>`: `decodeKeymapPayload`, `KeymapFrame`
  pack/unpack/CRC, `KeymapProtocol` chunk handling, and
  `LayerEngine.loadKeymap(binary:count:)` → `loadKeymap(_ bytes: Span<UInt8>)`.
- `decodeKeymapPayload` becomes `throws(KeymapDecodeError)` instead of returning
  nil; the upload path maps the error to its existing failure status (no protocol
  change).
- Wire format, `PayloadBuilder`, generators and `builderMatchesShellGenerator` are
  unchanged. Host tests are updated for the new signatures; new tests cover the
  256 cap and `KeyBitset`.

## Phase 4 — Existentials and ownership

- `protocol HIDTransport { func send(_ report: borrowing HIDReport) }`
  implemented by `BleHidTransport` (NimBLE on ESP32-C6; BTstack via
  `ports/common/BleHidGatt.swift`), `UsbHidTransport` (TinyUSB ports) and
  `Ch9350Transport` (ESP32-C6 UART). `Main.swift` holds
  `wired: any HIDTransport` and `ble: (any HIDTransport)?`; `ConnectionMode` selects
  one at runtime. The `send_keyboard_report`/`send_wired_report` symbol plumbing and
  its `#if`s leave the scan loop. `@c` entry points needed by C callbacks stay.
- `protocol KeymapStorage` implemented by `KeymapStoreNVS`, `KeymapStoreFlash`,
  and the stub stores; `KeymapProtocol` takes `any KeymapStorage` instead of injected
  closures; host tests use a `FakeKeymapStorage`.
- `protocol LEDChain` implemented by the RMT and PIO drivers; `RGBLighting` takes
  `any LEDChain` and is compiled for smk_kbd_rp2040 too (removing the
  `SMK_RGB_AVAILABLE` ESP32-only restriction where the only reason was the driver).
- `~Copyable` handles for the RMT channel, PIO state machine and the flash-write
  critical section.
- **Size fallback:** if a target exceeds the 2 % budget, the offending protocol is
  used as a generic constraint (`some HIDTransport` / `<T: HIDTransport>`) instead —
  same API, no boxing. armv6m targets (samd21, rp2040 family) are the likely trigger.
- Every new or moved SMKCore file is added to all six CMake source lists
  (`cross-target-impact-reviewer` agent run at phase end).

## Concurrency — out of scope (spike result)

A throwaway spike (2026-10-09, session scratchpad) measured Embedded Swift 6.4
concurrency:

- `_Concurrency` **does not exist** for `armv6m-none-none-eabi` or
  `riscv32-none-none-eabi` in 6.4.0, 6.3.x, or the 2026-05-27 snapshot — so ESP32-C6,
  RP2040 and SAMD21 cannot use async at all, which rules it out for shared code
  (`MacroPlayer`, `KeymapProtocol`).
- On armv7em it links, but needs a hand-written global executor
  (`swift_task_enqueueGlobalImpl`), 64-bit atomic libcalls, `memset_s`, and a
  hand-rolled tick sleep (`Task.sleep`/clocks are unavailable in Embedded).
  Cost: +15.6–24.1 KB flash, +0.6 KB static RAM, ~1.25 KB heap per task.

Revisit when a toolchain ships `_Concurrency` for armv6m and riscv32.

## Execution model

- Branch `swift-6.4-adoption`; one commit series per phase; PR at the end (or per
  phase if the maintainer prefers — decided in the plan).
- Each phase = one Workflow: parallel implementer agents partitioned by **file
  ownership** (shared `Sources/`, `ports/common`, then one agent per port family),
  then a single verifier agent that runs `tools/build_all.sh` and the
  cross-target-impact review, then a code-review pass. A phase that fails the gate
  is fixed before the next phase starts; nothing is merged past a red gate.
- Implementer reports are verified independently (git location/commits) before
  being trusted.
- Workflow size guideline is "< 10 agents" per run; larger phases (2, 4) are split
  into two runs.

## Risks

- **swift-mmio macro plugin in CMake** — the riskiest build change. Mitigation: Phase
  2 starts with a one-target (stm32f4) integration before fanning out.
- **Existential size on armv6m** — mitigated by the generic fallback.
- **swift-mmio on 6.4** — the pinned tag must build with 6.4; if no tag does, pin a
  commit and record it.
- **ESP-IDF interplay** — ESP32-C6 drives swiftc via a custom command; plugin and
  extra sources must be wired into that command, not CMake's Swift language support.
- **No hardware for most ports** — only builds are gated; the manual smoke test covers
  the three boards that exist.

## Out of scope

Concurrency; SVD-generated register definitions; wire-format or keymap-format
changes; replacing `@_extern(c)` where no header import exists; Unicode stub removal
(still required in 6.4); STM32WB license resolution.
