Architecture

SMK is written mostly in Embedded Swift, with a thin C layer for vendor SDK glue (ESP-IDF, pico-sdk, BTstack, TinyUSB) where the calling convention or struct-heavy config APIs make Swift impractical.

The Swift ↔ C Boundary

  • Sources/smk/Bridging.h — C headers imported into Swift; declares every C function callable from Swift.
  • Swift calls into C via @_extern(c, "fn_name") (BLE init, GPIO init, FreeRTOS delay, logging).
  • Swift exposes its entry point to C via @_cdecl("app_main_swift"), called from Sources/components/kb_main.c's app_main().

A real bug this project hit: volatile MMIO in Swift

Register-polling loops written in Swift must call an opaque C function inside the loop body (e.g. smk_cpu_nop()), because UnsafeMutablePointer.pointee is not a volatile access in Swift — LLVM treats an empty-bodied while (reg.pointee & bit) == 0 {} as loop-invariant and deletes it outright under the forward-progress rule, silently turning a hardware wait into no wait at all. This was found by disassembling the STM32 ports' clock-init code; any future port doing direct MMIO polling from Swift will hit it again.

Shared Swift Sources

Sources/smk/ and Sources/SMKCore/ compile into every target. Sources/SMKCore/ in particular has zero hardware/@_extern calls, so it's also exposed as a real, host-testable Swift Package library (SMK_HOST_TESTS_ONLY=1 swift test — no embedded toolchain required):

Key Architectural Patterns

Matrix scan direction depends on colsAreDriven in the board's compiled-in payload header (from boards/<name>.json), since different boards wire diodes/strobe direction oppositely — columns strobed and rows sensed on ESP32-C6's smk_kbd board (COL2ROW), rows strobed and columns sensed on RP2040 boards.

Layer resolution (LayerEngine.getAction) iterates layers from highest index to 0, skipping inactive layers and transparent keys, returning the first non-transparent action. Layer 0 is always active.

HID dispatch: each scan tick builds a HIDReport from all currently pressed key/modifier actions, then sends it via send_keyboard_report (BLE) or send_wired_report (CH9350 UART) depending on the active ConnectionMode.
